2.5 Методы обеспечения безопасности

Безопасность проекта сделана на стандартных механизмах Django и на аккуратной обработке запросов на фронтенде. Если сказать просто, пользователь входит в систему через сессию, опасные запросы идут только с CSRF-токеном, пароли не хранятся в открытом виде, а работа с базой данных идёт через ORM без ручного SQL.

2.5.1 Аутентификация и авторизация

В проекте используется сессионная аутентификация Django. Пользователь вводит логин и пароль на странице входа, потом сервер проверяет их через стандартную функцию authenticate. Если данные верные, сервер создаёт сессию через login и возвращает сведения о пользователе. При выходе из системы сессия закрывается через logout.

На фронтенде при запросах к серверу всегда передаётся credentials: include, чтобы браузер отправлял и принимал сессионные cookie. Для проверки текущего состояния пользователя есть отдельный запрос auth/me/, он просто смотрит, активна ли текущая сессия. Роль пользователя хранится в профиле и используется для разделения доступа внутри приложения и интерфейса.

2.5.2 Защита от CSRF

Для всех небезопасных запросов, таких как POST, PATCH и DELETE, используется CSRF-защита. Сервер отдаёт CSRF-токен через отдельный эндпоинт auth/csrf/. Фронтенд получает этот токен, сохраняет его в памяти и добавляет в заголовок X-CSRFToken перед отправкой запроса.

Дополнительно в настройках проекта включён middleware CsrfViewMiddleware, поэтому Django сам проверяет валидность токена. Если токен не передан или он неправильный, запрос блокируется. Это защищает приложение от поддельных запросов, которые могут быть отправлены от имени уже вошедшего пользователя.

2.5.3 Хеширование паролей

Пароли не сохраняются в базе данных в открытом виде. При создании пользователя сервер использует стандартный механизм Django, который сразу хеширует пароль перед записью в базу данных. При изменении пароля он тоже сначала преобразуется в хеш через встроенный метод set_password.

Проверка пароля при входе происходит не через прямое сравнение текста, а через встроенную функцию authenticate. Это безопаснее, потому что реальный пароль не хранится в базе и не передаётся в открытом виде после входа.

2.5.4 Защита от SQL-инъекций

Работа с базой данных выполняется через Django ORM, а не через ручные SQL-запросы. Для создания, изменения и чтения данных используются модели, сериализаторы и методы типа create, filter, get и save. За счёт этого значения полей обрабатываются как параметры, а не как часть SQL-строки.

Дополнительная защита появляется за счёт валидации данных в сериализаторах и представлениях. Например, сервер отдельно извлекает поля профиля пользователя, проверяет роль, связывает пользователя с подразделением и не собирает запросы из сырого текста. Это уменьшает риск внедрения вредоносных SQL-команд.

2.5.5 Безопасность файловых операций

Загрузка файлов в проекте реализована через Django FileField и поддержку multipart-запросов. Фотографии оборудования сохраняются в папку media/equipment_photos/. Имя файла формируется автоматически механизмами Django, поэтому файл не записывается вручную в произвольное место на диске.

Файлы передаются только через отдельный запрос добавления оборудования, а не как текст внутри обычного JSON. Это делает обработку понятнее и снижает риск ошибок при сохранении. Хранилище файлов вынесено в отдельную папку media, а путь к ней задаётся через MEDIA_ROOT и MEDIA_URL.

2.5.6 Передача данных между фронтендом и сервером

Фронтенд не отправляет лишние данные в открытом виде. Для обычных запросов используется JSON, а для файлов используется FormData. Перед каждым запросом вызывается единая вспомогательная функция, которая автоматически добавляет CSRF-токен, ставит credentials: include и обрабатывает ошибку ответа.

Если сервер возвращает ошибку, приложение не продолжает работу с неверными данными, а показывает ошибку пользователю и останавливает операцию. Такой подход снижает риск случайной порчи данных и делает поведение системы предсказуемым.
